3. **Defensive Static Boundaries (7 branches)**: Lines 339, 376, 495, 508, 620, 629, 630, 639, and 724 represent static capacity limits (8-slot buffer bounds), duplicate caller diagnostics, and short-circuit compound branches for unreachable state combinations under class contracts.

## 3. Coverage Gap Findings

The report's most important uncovered items are not missing lines or missing decisions in the selected business/control logic. They are branches that the local native functional-test build cannot exercise for reasons that are structural, environmental, or defensive rather than test omissions.

The largest gap is the 26 compiler-generated exception-unwinding legs. These appear in the GCC branch log as landing pads around destructor cleanup and around the logging macros used by `PX4_ERR` and related helpers. In the student's local environment the test target is built with GCC coverage flags, the code is compiled for native Linux, and the runtime is a deterministic single-threaded functional test. Under those conditions exceptions are not thrown, so the false branch of those landing pads is never taken. A human reviewer examining the source can see the same thing: the associated objects are local stack objects and logging macros, and there is no `throw` site reachable from the tested functions under normal use. The gap is therefore a measurement artifact of which compiler paths the test harness can reach, not evidence that a real decision outcome is untested. Coverage of the surrounding source decisions is complete; the uncovered legs are artifacts of branch instrumentation, not of missing test intent.

The six platform preprocessor branches are a scope limitation, not a test-quality deficiency. The lines 181–183 and 523–525 blocks are guarded by `#ifdef EMSCRIPTEN_BUILD`, which means they are compiled only for a different target platform and are physically absent from the native Linux x86_64 binary used for the evidence. The student's local environment is not an Emscripten/WebAssembly build, so those branches are not reachable in the submitted evidence. A broader conclusion would require either building and testing that platform variant or explicitly excluding the platform path as out of scope. The team chose the latter and documented it, because the assignment asks for coverage of the selected business/control logic, not of every build configuration of the whole repository.

The defensive static-boundary and short-circuit branches are the smallest and most clearly justified group. The eight-slot action buffer has a hard capacity of eight active distinct callers; the full-buffer replacement and drop logic in `TC-FS-16` exercises the reachable side of that design, but the extreme combinations that would require more than eight simultaneously active distinct callers, or the duplicate-caller diagnostic path, are guarded by class-level contracts and are not expected to occur in normal operation. These branches exist to make misbehaving callers visible rather than to implement ordinary control flow. They are reachable only under invalid internal states that the test harness deliberately does not construct, because doing so would move the exercise away from the intended operational semantics of the component.

Taken together, the remaining gaps have a consistent theme: they are branches that cannot be reached in the local native functional-test configuration without changing the compiled binary, the runtime model, or the operational assumptions under which the component is meant to run. None of them represent an uncovered executable production decision in the selected scope. That distinction matters for the final judgment, because it means the missing percentage is not missing test effort on the analyzed logic.

## 4. Suggested Improvements

If the team wanted to strengthen the submission beyond the current evidence, the first concrete improvement is a second coverage capture on a different build configuration, not more tests on the same one. Building the same test binary for the WebAssembly/Emscripten target, or running the suite under a coverage toolchain that reports condition-level outcomes more directly, would convert several of the current "unreachable in this build" branches from "unexplained" to "explicitly scoped out." Even if the result is still a gap, the gap would then be tied to an explicit platform decision instead of to the local environment alone. That directly addresses the assignment's instruction that "hardware dependent" by itself is not enough and that difficult-to-test logic must not be excluded merely to improve the reported percentage.

A second concrete improvement is simulator or integration-level support for the integration risk the unit suite cannot see. `FailsafeBase` decides what action the vehicle should take, but it does not by itself prove that the chosen action propagates correctly through uORB, mode transitions, timer behavior under load, or real actuator feedback. A small set of PX4 SITL or functional integration tests could exercise the same `FailsafeBase` output in a fuller flight-controller context, especially for timing-dependent deferral, mode fallback under concurrent status changes, and takeover behavior when several subsystems are active at once. That would not change the unit coverage results, but it would extend confidence to the integration boundaries the report currently lists as residual risk.

A third concrete improvement is tighter dependency control for the defensive and timing-sensitive paths. The duplicate-caller and full-buffer branches are hard to reach with a normal operational harness because they depend on violating internal contracts. A test design could make those paths reachable by adding a controlled test seam that temporarily injects repeated caller IDs or extra simultaneous action slots without altering production behavior, and then immediately restoring the normal seam. If such a seam were justified and documented, the otherwise-defensive branches would become testable instead of remaining classified as defensive. The trade-off is that it would add test-only machinery, so it should only be done if the team is willing to defend the added seam in the viva.

A fourth concrete improvement is refactoring for observability rather than for coverage. Several of the gaps are not hard to test because the logic is complex; they are hard to test because the relevant state is internal and the production code is written to minimize test access. Introducing a small amount of test-only observability, or separating the defensive diagnostics from the operational path more clearly, would make future verification easier without changing the behavior that matters. This is the kind of improvement the assignment points to when it mentions instrumentation and refactoring for testability.

None of these are required to submit the current work. They are concrete next steps that would address the specific residual gaps and risks the team already identified.

## 5. Engineering Quality Judgment

The structural evidence supports a strong but scoped conclusion about the tested logic. On the evaluated scope, the student suite executes 100% of the executable statements and functions in `framework.cpp` and `framework.h`, demonstrates both outcomes of every reachable production decision in that scope, and completes MC/DC for the safety-critical pilot-takeover compound decision with 10 of 10 independence pairs. That is a substantial result for the component the team selected and analyzed, and it is reproducible from the submitted test code, the recorded baseline, and the final coverage evidence rather than from a claimed percentage alone.

What the evidence does not support is any broader claim about PX4 as a whole. The suite covers one cohesive control component under controlled inputs. It does not cover upstream subsystems that feed failures into `FailsafeBase`, the uORB propagation layer, the mode and actuator side of the vehicle, sensor noise, multi-threaded timing races, or the platform-specific and compiler-generated branches that remain zero-hit in the local build. MC/DC guarantees independence of the analyzed atomic conditions under unit-level inputs; it does not guarantee that the surrounding system will present those conditions the way the tests assume.

The confidence the coverage provides is therefore high for the question "does this specific state machine behave deterministically according to its design under the conditions we could construct?" and limited for any wider question. The remaining 9.2% of branch legs are explained as compiler exception-unwinding artifacts, platform preprocessor exclusions, and defensive static boundaries rather than as missed test design. That explanation is defensible for the selected scope, but it depends on the local native functional-test build and on the team's decision to treat those paths as out of scope. A reviewer should not generalize this result to the entire repository or to real flight behavior.

In short, the submission demonstrates that the chosen `FailsafeBase` logic is thoroughly exercised for the behaviors the team set out to verify, and it documents honestly where the evidence stops. That is the correct kind of conclusion for this assignment: strong for the analyzed component, explicit about the limits, and careful not to overclaim.
